# V0.9.87I MVP OOM Memory Audit

## Finding
The `geffenia_mvp_arena_3x3_region_camera` map contains 51 unique MVP species. The previous world-monster asset cache had no entry or decoded-memory limit and off-screen entities retained `_animation.asset`. Walking/AFKing across the arena could therefore keep every decoded MVP atlas alive.

Using the real atlas image dimensions in this release and 4 bytes/pixel RGBA, all 51 MVP atlases sum to **602.375 MiB decoded image memory**. This excludes Canvas backing stores, animation JSON/maps, skill effects, DOM nodes, inventory/save serialization and browser overhead.

Largest examples:
- 1885 闇影龍: 2048×3776 ≈ 29.50 MiB
- 2131 失落之龍: 2048×3632 ≈ 28.38 MiB
- 2022 尼德霍格的影子: 2048×3584 ≈ 28.00 MiB
- 2251 喬伊亞: 2048×3536 ≈ 27.62 MiB
- 2190 暴力腔棘魚: 2048×3472 ≈ 27.12 MiB
- 2529 蠕蟲女王: 2048×3392 ≈ 26.50 MiB

## Mitigation
- MVP arena cache target: desktop 12 entries / 160 MiB, coarse-pointer 8 / 96 MiB.
- Normal map target: desktop 18 / 224 MiB, coarse-pointer 12 / 128 MiB.
- LRU only evicts assets not currently rendered.
- Off-screen monster DOM teardown also drops the entity's atlas reference.
- Map teardown clears decoded atlas cache.
- Async decode generation guard prevents a stale previous-map decode from repopulating cache.
- MVP visual preload padding reduced from the general 260px valve to at most 120px.
- Death reward queue stores slim reward data, not source monster / Canvas / atlas runtime references.

## Drop-rate check
`applyRate(value, "drop")` multiplies the chance by the configured rate. The loot path then caps the final basis-point chance at 10000. The current 100× drop setting therefore increases/caps drop probability; it does not repeat the loot loop 100 times. It can still increase inventory/log/save pressure because more rows actually drop, but it is not the unbounded atlas-retention mechanism found above.
